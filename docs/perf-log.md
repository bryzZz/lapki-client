# Журнал замеров производительности холста

Здесь записывается, что меряли и что получилось на каждом шаге оптимизации. Как мерить, описано в [perf.md](perf.md).

Правила:

- каждый шаг — одно изменение и один коммит, вместе с записью в этом журнале;
- после каждого шага: snapshot test, `npm run perf:bench`, `__perf.run()` в приложении и ручной чек-лист из `perf.md`;
- сравниваем с baseline и с предыдущим шагом на тех же схемах и в том же окружении.

## Окружение

|            | Бенчмарк (`perf:bench`)                          | Приложение (`__perf.run()`)             |
| ---------- | ------------------------------------------------ | --------------------------------------- |
| Где        | Node v23.7.0, jsdom, canvas заглушен             | `npm run dev` в WSL (WSLg)              |
| Железо     | AMD Ryzen 5 7500F                                | то же                                   |
| Холст      | 1920×1080                                        | 1614×1334                               |
| Браузер    | —                                                | Chromium 112.0.5615.204 (Electron)      |
| Что меряет | только наш JS: обход дерева, геометрия, hit-test | всё вместе: JS + растеризация + браузер |

В WSL canvas, похоже, растеризуется процессором, поэтому абсолютные цифры в приложении завышены. Сравнивать нужно между шагами в одном окружении.

Схемы: `demos/perf/` — `flat-200` (200 состояний, глубина 1), `medium-depth3` (104, глубина 3), `deep-depth6` (63, глубина 6), `large-depth4` (320, глубина 4).

### Выводы по baseline

- Цель (p95 кадра ≤ 16 мс) в приложении не достигается ни на одной схеме, кроме сценария hover.
- **Bottleneck 1 — геометрия вложенности (P1)** (`Shape.computedWidth`/`childrenContainerHeight`): число вызовов растёт экспоненциально с глубиной. На `deep-depth6` это ~85% времени бенчмарка, на `large-depth4` ~50%.
- **Bottleneck 2 — рисование всей схемы (P2)**: в приложении отрисовка в 2–6 раз дольше бенчмарка, то есть основное время уходит на canvas. При этом на экран попадает 4–12% схемы (`large-depth4`: 13 из 320 состояний).

## Шаг 1. Геометрия вложенности без экспоненты

Коммит: «Геометрия вложенности Shape без экспоненциального пересчёта». Файл: `src/renderer/src/lib/drawable/Shape.ts`.

**Что изменено (P1).** В `computedWidth` и `childrenContainerHeight` геометрия каждого ребёнка считается один раз за вызов. Раньше внутри цикла заново пересчитывалась геометрия текущего «крайнего» ребёнка вместе со всем его поддеревом. Результат вычислений тот же.

**Проверка корректности.**

- Snapshot test: пройден без обновления (геометрия, hit-test, хеш отрисовки совпали). Время теста упало с ~80 с до ~8 с.
- Ручной чек-лист: пройден. Подсказки не проверены: в чек-листе не было сказано, где они должны появляться (уточнено в `perf.md`).

## Шаг 2. Отсечение по viewport (P2)

Коммит: «Отсечение невидимых фигур при отрисовке холста». Файлы: `src/renderer/src/lib/basic/EditorView.ts`, `src/renderer/src/lib/utils/index.ts`.

**Что изменено (P2).** `EditorView.draw` перед `child.draw()` проверяет, пересекается ли фигура с холстом (с запасом `50 / scale` на выделение, «хваталки» и концы стрелок). Для перехода берётся общий прямоугольник источника, цели и метки — стрелка лежит внутри него. Детей обходим всегда, даже если родитель отсечён: вложенная фигура может выходить за рамку родителя.

**Проверка корректности.**

- Snapshot test: `bounds` (геометрия) и `hits` (hit-test) не изменились; изменились только `drawHash`/`drawCalls` в 18 из 21 положения камеры (меньше вызовов canvas) — снимок обновлён.
- Новый тест `culling.test.ts`: для каждой отсечённой фигуры на всех demo и 5 камерах записываются вызовы canvas, которые она сделала бы, и проверяется, что ни одна линия, фигура или текст не попадает на холст. Тест ловит ошибку: при запасе −300 вместо 50 падают все 7 схем.
- Побочные эффекты в `draw()`: единственный — `Events.drawImageEvents` пишет `currentEventRows`, но его читатель `Events.update` перед чтением пересчитывает значение сам. Пропуск `draw()` не влияет на размеры.
- Ручной чек-лист: полностью не проходили. Перетаскивание, выделение и отрисовка проверены при ручных замерах ниже, проблем не замечено.

### Ручное перетаскивание после шага 2

При ручной проверке в dev-режиме плашка FPS при перетаскивании маленького состояния (камера приближена) показывала: падение до ~20, пролаг, потом ~30. Плашка считает FPS за последнюю секунду, поэтому «20» и «пролаг» — это нажатие (P11, в dev ~500 мс) и разовый рендер дерева иерархии в dev; «30» — само перетаскивание.

Профиль ручного перетаскивания в production (`npm run build` + `npx electron .`, WSL, камера приближена к одному состоянию): ~35 кадров/с, ~28 мс на кадр.

| Что                          | На кадр   | Комментарий                                                                                                                           |
| ---------------------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `Paint` браузера             | ~7 мс     | вывод canvas на страницу; в WSL, вероятно, программный                                                                                |
| Наша отрисовка (`view.draw`) | ~5–9 мс   | холст почти пуст, но проверка видимости считает `drawBounds` для всех фигур (для перехода — трижды); `drawBounds` — 17% всего времени |
| Обработчик `mousemove`       | ~2.5–6 мс | hit-test для подсказок на каждое движение мыши даже при зажатой кнопке (P3)                                                           |
| Сборка мусора                | ~1.4 мс   | `drawBounds` создаёт новые объекты на каждый вызов                                                                                    |

Нажатие на состояние — 128–157 мс, отпускание — 89 мс (P11).

### Вывод

- При обычной камере отрисовка в 4 раза быстрее (37 → 9 мс), FPS в сценариях 17–20 → 32–53.
- При видимой целиком схеме без изменений (P6).
- При ручном перетаскивании узким местом стала наша геометрия: проверка видимости (цена P2) и hit-test подсказок (P3) многократно пересчитывают `drawBounds`. Следующие шаги — P3, затем P5.
